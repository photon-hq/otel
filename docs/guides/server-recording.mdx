---
title: "Server request and response recording"
description: "Record incoming HTTP and unary RPC payloads as trace-correlated OTLP logs."
---

Server recording is opt-in. It emits structured **DEBUG OTLP logs only**; it
does not mirror bodies to console and is independent of `createLogger`'s
`LOG_LEVEL` gate. Configure an OTLP logs endpoint or an external logger provider.

The recorders capture content at adapter boundaries. They do not create server
spans, extract incoming trace headers, authenticate requests, or install framework
middleware. Start a recording inside the framework's existing server span, or pass
an explicit OpenTelemetry `context`. Each exchange also gets a `recordId` so its
request, response, and error records can be paired without a trace.

## Runnable HTTP example

Save this as `server.ts` in a Bun project with `@photon-ai/otel` and
`@opentelemetry/api` installed. This demo uses an illustrative inventory response,
not the Cosmos API contract. It expects an OTLP/HTTP collector on port 4318;
`OTEL_EXPORTER_OTLP_ENDPOINT` can override that endpoint.

```ts
import { context, propagation, SpanKind } from "@opentelemetry/api";
import { serve } from "bun";
import { createHttpServerRecorder, setupOtel } from "@photon-ai/otel";

const otel = setupOtel({
  serviceName: "inventory-recording-example",
  endpoint: "http://localhost:4318",
  instrumentFetch: false,
});
const tracer = otel.tracerProvider.getTracer("inventory-example");
const recordHttp = createHttpServerRecorder({ record: { preset: "bounded" } });

const server = serve({
  hostname: "127.0.0.1",
  port: Number(process.env.PORT ?? 3000),
  fetch(request) {
    const parent = propagation.extract(
      context.active(),
      Object.fromEntries(request.headers)
    );
    return tracer.startActiveSpan(
      "inventory request",
      { kind: SpanKind.SERVER },
      parent,
      (span) => {
        const requestId =
          request.headers.get("x-request-id") ?? crypto.randomUUID();
        const recording = recordHttp(request, { requestId });
        try {
          const url = new URL(request.url);
          const lines = url.searchParams.has("empty")
            ? []
            : [{ id: "line-1", availability: "unavailable" }];
          const response = Response.json(
            url.pathname === "/lines" ? { lines } : { error: "Not found" },
            {
              status: url.pathname === "/lines" ? 200 : 404,
              headers: { "x-request-id": requestId },
            }
          );
          recording.response(response);
          return response;
        } catch (error) {
          recording.error(error);
          throw error;
        } finally {
          span.end();
        }
      }
    );
  },
});

async function shutdown() {
  await server.stop();
  await otel.shutdown();
}

process.once("SIGINT", shutdown);
process.once("SIGTERM", shutdown);
```

```sh
bun server.ts
```

In another terminal, compare a populated response, an empty response, and a 404:

```sh
curl -H 'x-request-id: example-populated' http://127.0.0.1:3000/lines
curl -H 'x-request-id: example-empty' 'http://127.0.0.1:3000/lines?empty'
curl -H 'x-request-id: example-not-found' http://127.0.0.1:3000/missing
```

The sample creates its own server spans. In an instrumented framework, use its
existing server span instead. The recorder calls themselves do not create spans.
For a service with an existing logger provider, keep that provider and omit the
additional `setupOtel()`; drain `flushServerRecords()` before closing its exporters.

## HTTP: WHATWG Request and Response

Create one recorder per server or policy, not once per request. Its admission
counter limits concurrent body captures across requests.

`redactUrl` transforms request and response URLs only in recorded telemetry;
it does not change application URLs. Without it, URLs are recorded unchanged.
If it throws, the recorded URL becomes `REDACTED`.

```ts
import { createHttpServerRecorder } from "@photon-ai/otel";

const recordHttp = createHttpServerRecorder({
  record: { preset: "bounded" },
  redactUrl: (url) => {
    const parsed = new URL(url);
    parsed.searchParams.delete("token");
    return parsed.toString();
  },
});

async function handle(request: Request): Promise<Response> {
  const recording = recordHttp(request, {
    requestId: request.headers.get("x-request-id") ?? undefined,
  });
  try {
    const response = await applicationHandler(request);
    recording.response(response);
    return response;
  } catch (error) {
    recording.error(error);
    throw error;
  }
}
```

`applicationHandler` represents the application's final HTTP handler. Call
`response()` with its final serialized `Response`, including handled 4xx/5xx
responses, before its body is consumed. An Elysia adapter must include mounted
routes, validation/error responses, and any response-transforming hooks. A
handler-level JavaScript return value is not necessarily the final HTTP response.

The recorder reads a clone and returns no replacement body. It preserves the
application's original request/response. A body already consumed or locked is
recorded as `unavailable_body`; a complete bodyless 204 response is distinct.
An unhandled exception creates an error record without fabricating a response.
If another middleware converts that exception into an HTTP response, record at
that outer response boundary instead.

For both HTTP and RPC, call `response()` on success or `error()` on an unhandled
failure so the recording can finish. The first `response()`, `error()`, request
abort, or shutdown completion wins; later terminal calls are ignored.
The response record means the adapter observed a response, not that the peer
received every byte. Socket delivery and response-body capture are separate facts.

## Unary Connect / gRPC

The RPC recorder accepts synchronous JSON-producing functions. The adapter owns
schema-aware serialization; use protobuf `toJson()` to preserve 64-bit integers,
enums, bytes, timestamps, and presence semantics.

```ts
import { toJson } from "@bufbuild/protobuf";
import { Code, ConnectError, type Interceptor } from "@connectrpc/connect";
import { createRpcServerRecorder } from "@photon-ai/otel";

const recordRpc = createRpcServerRecorder({
  record: { preset: "bounded" },
});

export const recordUnary: Interceptor = (next) => async (request) => {
  if (request.stream) {
    return next(request);
  }
  const recording = recordRpc({
    service: request.service.typeName,
    method: request.method.name,
    system: request.header.get("content-type")?.startsWith("application/grpc")
      ? "grpc"
      : "connectrpc",
    headers: request.header,
    signal: request.signal,
    message: () => toJson(request.method.input, request.message),
  });
  try {
    const response = await next(request);
    if (!response.stream) {
      recording.response(
        () => toJson(response.method.output, response.message),
        { headers: response.header },
      );
    }
    return response;
  } catch (error) {
    recording.error(error, Code[ConnectError.from(error).code]);
    throw error;
  }
};
```

Place this interceptor **inside tracing and outside authentication/validation**
so rejected RPCs are recorded with the same server context. Install it on every
listener (for example, both direct and staff faces). HTTP/protocol rejections
before Connect interceptors run require transport-level recording.

The interceptor above is intended for a service that already initializes OTel.
Add `recordUnary` after its server tracing interceptor and before its auth
interceptor in the listener's interceptor list. Keep its generated protobuf
schemas and existing handler unchanged; the adapter supplies `toJson()` output
to the recorder. Neither creating `recordRpc` nor upgrading this package installs
that interceptor automatically.

`error(error, code)` accepts the adapter's RPC status name; omitted codes are
`UNKNOWN`. HTTP 200 is not used to infer RPC success. Response records use
`code: "OK"`. Request aborts use `CANCELLED`.

Message functions run synchronously when admitted, and their JSON is snapshotted
before returning. Their exceptions, cycles, unsupported objects, BigInt, NaN,
or promises produce an incomplete `serialization_error` capture, not a handler
exception. They do not run when byte limits are zero or admission is exhausted.
Limits bound retained capture bytes; they do not bound the adapter serializer's
own CPU or temporary allocations. Keep serializers synchronous and side-effect free.

This API records **unary messages**. It does not iterate an RPC AsyncIterable or
buffer an entire long-lived stream. The sample leaves streaming methods to a
separate per-message adapter. It records logical protobuf output before transport
encoding, not HTTP/2 frames, trailers, or a client delivery acknowledgment.

## Content policy

Both recorders require an explicit `record` preset, with the same defaults and
options as [fetch recording](./fetch-instrumentation.mdx#request-and-response-recording):

| Preset | Bytes per direction | Body deadline | Concurrent captures | Headers |
| --- | --- | --- | --- | --- |
| bounded | 1 MiB | 30 s | 32 | Allowlist |
| full | Unlimited | Unlimited | Unlimited | All |
| custom | Unlimited | Unlimited | Unlimited | All |

For RPCs, `parseRequest` receives a `RpcRequestRecord`, and `parseResponse`
receives a `RpcResponseRecord`. HTTP uses `FetchRequestRecord` /
`FetchResponseRecord`; the HTTP request's fetch-only `options` object is empty.

Bodies are lossless captured UTF-8 or base64 bytes. No preset automatically
redacts body fields. `full` and `custom` also include credentials in headers
unless explicitly restricted. An example response-body policy is:

```ts
const recordRpc = createRpcServerRecorder({
  record: {
    preset: "custom",
    headers: ["content-type", "x-request-id"],
    maxBodyBytes: 1024 * 1024,
    bodyTimeoutMs: 30_000,
    maxConcurrentCaptures: 32,
    onParserError: "omit",
    parseResponse: (record) => {
      const value = JSON.parse(record.body?.data ?? "null");
      return { code: record.code, result: redactResponse(value) };
    },
  },
});
```

`redactResponse` is application policy, not a built-in function. Use
`onParserError: "omit"` when a parser removes secrets. The default raw fallback
is intended for parsers that do not enforce redaction.

Capacity rejection still emits metadata with `capture.complete=false` and
`reason=capacity_limit`. Size/time limits, consumed bodies, aborted reads,
serialization failures, and shutdown are also explicit. A bounded record is not
a promise of a complete response: inspect `capture` and `parserError`.

## Logs and lifecycle

Events are `photon.http.server.request/response/error/incomplete` and
`photon.rpc.server.request/response/error/incomplete`.

The envelope contains `schemaVersion`, `recordId`, `operation`, optional
`requestId`, `startedAt`, and `finishedAt`. Terminal records also include
`completedAt` and `durationMs` measured when the adapter completed the call,
separately from asynchronous capture completion. Payload records contain
`direction`, `capture`, and `payload`; custom parsers replace `payload`.
A capture retains the logger provider and context selected when it began.

`recording.done` waits for that exchange's captures/parsers to settle; it does
not flush exporters. Do not await it before returning a business response.
`flushServerRecords({ timeoutMs })` drains recordings started before the call;
`timeoutMs` is measured in milliseconds and defaults to `5000`. It accepts
nonnegative integers up to `2147483647`, or `Infinity` to wait without a deadline.
At the deadline, pending bodies/parsers are finalized as partial, and calls
without a terminal outcome emit
`incomplete` with reason `shutdown`. Late completions cannot create duplicate
terminal records. This does not stop application handlers or their streams.

`setupOtel().shutdown()` drains both fetch and server recordings before closing
the providers. With external providers, call `flushServerRecords()` before
flushing/closing your exporters. The existing `flushFetchRecords()` continues
to drain fetch recordings only.

## Find the example records in SigNoz

Open Logs and filter by `service.name = inventory-recording-example`, allowing
DEBUG severity. Search for the example request ID in the structured log body.
The HTTP response event name is `photon.http.server.response`; unary RPC uses
`photon.rpc.server.response`. Event-name display and body indexing depend on the
collector and SigNoz configuration, so inspect the raw structured body if a field
is not available as a filter.

For the three HTTP calls above, inspect these fields inside the log body:

| Request ID | `payload.status` | `payload.body.data` |
| --- | --- | --- |
| example-populated | 200 | `{"lines":[{"id":"line-1","availability":"unavailable"}]}` |
| example-empty | 200 | `{"lines":[]}` |
| example-not-found | 404 | `{"error":"Not found"}` |

Each of these small responses should have `capture.complete=true` and
`payload.body.encoding=utf8`. `recordId` (also exported as the `record.id`
attribute) pairs the request and response logs; the log's trace/span IDs link to
the server span. RPC records expose `payload.code` and `payload.body.data`;
the latter contains the serialized ProtoJSON.

Check `capture.complete`, `capture.reason`, and `parserError` before interpreting
a missing payload as an empty response. An empty JSON array is recorded content;
an incomplete capture or omitted parser result is missing evidence. An exception
without an observed response has an `.error` event instead of a fabricated body.
